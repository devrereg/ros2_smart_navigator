## 1. 프로젝트 개요

### 목표

ROS 2와 Gazebo 시뮬레이션 환경에서 TurtleBot3 Burger를 활용해 LiDAR 기반 장애물 회피 기능을 구현하고, 별도의 벤치마크 토픽에서 DDS QoS 설정에 따른 메시지 전달 성능을 비교·분석한다.

### 현재까지 완료된 준비

- [x] 팀원별 기존 교육 환경에서 ROS 2 및 Gazebo 실행 확인
- [x] 로봇 모델 선정: **TurtleBot3 Burger**
- [x] 시뮬레이션 맵 선정: **Robotnik 실험실 월드**
- [x] 노드 및 토픽 인터페이스 안정화
- [x] GitHub 저장소 생성

### 선택한 맵

- 저장소: <https://github.com/RobotnikAutomation/robotnik_gazebo_worlds>
- 실행 명령:

```bash
ros2 launch robotnik_lab_world robotnik_lab_world.launch.py
```

> 실행 패키지와 launch 파일 이름은 현재 교육 환경에서 확인한 값을 기준으로 한다. 팀원들의 ROS 2 배포판과 패키지 설치 상태가 일치하는지 프로젝트 시작 시 기록한다.

## 2. 핵심 결과물

1. **LiDAR 기반 장애물 감지 노드** — `/scan` 데이터를 받아 전방 장애물 거리를 계산한다.
2. **장애물 회피 노드** — 감지 결과에 따라 정지·회전·재주행 명령을 생성한다.
3. **ROS 2 통합 실행 절차** — 팀원이 재현할 수 있는 launch 또는 명령어 기반 실행 절차를 제공한다.
4. **DDS QoS 벤치마크** — 별도 테스트 토픽에서 `BEST_EFFORT`와 `RELIABLE` 등의 조건을 비교한다.
5. **실험 데이터와 분석 결과** — CSV, 그래프, 실험 조건 및 해석을 GitHub에 정리한다.

## 4. 시스템 구성 및 인터페이스

### 기본 데이터 흐름

```text
Gazebo: Robotnik 실험실 월드 + TurtleBot3 Burger
                    |
                    v
             /scan (LaserScan)
                    |
                    v
         장애물 감지 / 회피 로직
                    |
                    v
             /cmd_vel (Twist 계열)
                    |
                    v
             TurtleBot3 주행
```

### 주요 노드

| 구성 요소 | 책임 |
|---|---|
| Gazebo 시뮬레이션 | 실험실 환경과 TurtleBot3 모델 제공 |
| `sensor_monitor` (선택) | `/scan` 데이터 수신 및 센서 상태 확인 |
| `obstacle_avoider` | `/scan` 처리 및 `/cmd_vel` 주행 명령 생성 |
| `experiment_monitor` | 벤치마크 메시지 수신·측정·CSV 기록 |

> `/scan`은 일반적으로 `sensor_msgs/msg/LaserScan`을 사용한다. `/cmd_vel`은 모델 및 설정에 따라 `geometry_msgs/msg/Twist` 또는 `TwistStamped`일 수 있으므로 실제 환경에서 `ros2 topic info` 등으로 확인한다. 기존에 안정화한 인터페이스를 우선 유지한다.

### 기본 확인 명령

```bash
# 실험실 월드 실행
ros2 launch robotnik_lab_world robotnik_lab_world.launch.py

# 토픽 목록 확인
ros2 topic list

# 토픽 타입과 Publisher/Subscriber 확인
ros2 topic info /scan
ros2 topic info /cmd_vel

# 메시지 내용 확인
ros2 topic echo /scan
```

## 7. QoS 실험 설계

### 목적

DDS QoS 설정에 따라 메시지 전달 특성이 어떻게 달라지는지 관찰하고, 측정 결과를 수치와 그래프로 설명한다.

### 권장 실험 항목

| 항목 | 계획 |
|---|---|
| Reliability | `BEST_EFFORT` vs `RELIABLE` |
| 발행 주기 | 예: 10 Hz와 50 Hz |
| 측정 지표 | 발행 수, 수신 수, 누락률, 지연시간 |
| 반복 횟수 | 조건별 최소 3회 |
| 데이터 저장 | CSV |
| 시각화 | 조건별 수신율·지연시간 그래프 |

### 실험 시 주의사항

- 주행 제어 토픽과 별도의 `/benchmark/...` 토픽을 사용해 주행 기능과 실험을 분리한다.
- 메시지 크기, 발행 주기, 실험 시간 등 비교 조건을 통제한다.
- Publisher와 Subscriber의 QoS 호환성을 확인하고 실제 연결 여부를 기록한다.
- 서로 다른 컴퓨터의 시계를 비교하는 경우 시간 동기화 오차를 고려한다. 가능하면 단일 컴퓨터의 동일한 시간 기준을 활용한다.
- 로컬 환경에서 메시지 손실이 발생하지 않아 조건 간 차이가 거의 없더라도 이를 그대로 결과로 기록한다. 결과를 과장하거나 임의로 손실을 만들지 않는다.
- 실험 결과에는 실행 환경, QoS 설정, 반복 횟수, 측정 방법 및 한계를 함께 기록한다.

## 11. 기술 면접 대비 질문

- ROS 2에서 Node, Topic, Publisher, Subscriber는 어떤 역할을 하는가?

- `BEST_EFFORT`와 `RELIABLE`의 차이는 무엇인가?
- Publisher와 Subscriber의 QoS가 호환되지 않으면 어떤 일이 발생하는가?
- LaserScan의 각도·거리 데이터에서 전방 장애물을 어떻게 판단했는가?
- `NaN`, `inf`, 센서값 미수신 상황은 어떻게 처리했는가?
- 회피 로직에서 정지·회전·재주행 기준을 어떻게 정했는가?
- 메시지 누락률과 지연시간을 어떤 방식으로 측정했는가?
- 로컬 환경에서 QoS별 차이가 작게 나왔다면 어떻게 해석할 것인가?
- 구현 과정에서 발생한 문제와 해결 방법은 무엇인가?
