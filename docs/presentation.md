## 시연 절차

```bash
pkill -f "gz sim"                      # 이전 시뮬레이션 정리
source install/setup.bash
ros2 launch obstacle_avoider avoid.launch.py world:=warehouse x_pose:=8.0 y_pose:=0.0
```

- 보여 줄 것: 직진 → 감속(`SLOW`) → 정지(`STOP`) → 회전(`ROTATE`) → 재주행. 터미널의 상태 전환 로그를 함께 띄운다.
- `(8.0, 0.0)`은 5일차에 정지·회피가 확인된 위치다. `(5.0, -6.0)`, `(-8.0, -8.0)`은 스폰 직후 끼이므로 쓰지 않는다.
- Gazebo가 처음 실행되면 Fuel 모델을 내려받으므로 발표 전에 한 번 실행해 둔다.

**실패 대비**

| 상황 | 대응 |
|---|---|
| Gazebo가 뜨지 않음 | `media/demo/`의 녹화본 재생 |
| 로봇이 움직이지 않음 | `ros2 topic echo /obstacle/front_distance`로 감지 확인. 없으면 녹화본 |
| 접촉·이상 동작 | 알려진 한계(정면 밖 장애물)로 설명하고 녹화본으로 정상 동작 제시 |

녹화본과 스크린샷은 발표 전에 `media/demo/`, `media/screenshots/`에 저장한다 (공동).

## QoS 결과 설명 틀

결과가 나오면 아래 순서로 말한다. 수치는 `stats.csv`의 값만 쓴다.

1. 설계: 2×2 요인, 조건별 10회, 블록 안 무작위 순서, 실행 1회가 표본 1개.
2. 손실률: 조건별 평균과 Wilcoxon p값. 모두 0%이면 "로컬 loopback에서는 손실이 없어 차이를 볼 수 없었다"로 그대로 말한다.
3. 지연: Reliability 주효과의 p값, 효과크기, 차이의 95% CI. 유의해도 차이가 수 μs라면 실용적 의미가 작다고 함께 말한다.
4. 한계: 단일 컴퓨터, 64바이트 한 크기, Python 노드 스케줄링 시간 포함.

## 예상 질문과 답변 요점

### A — 시스템 설계·통합

| 질문 | 답변 요점 |
|---|---|
| 왜 감지와 회피를 노드로 나눴나 | 따로 시험하기 위해. 회피는 거리 토픽만 발행해 Gazebo 없이 시험했다 |
| 노드 간 인터페이스를 왜 `Float32` 하나로 했나 | 회피에 필요한 정보가 정면 최소 거리뿐이라 최소한으로 했다. 대신 타임스탬프가 없어 검증 노드는 수신 시각으로 짝짓는다 |
| `/cmd_vel`이 왜 `TwistStamped`인가 | Jazzy + Harmonic의 `ros_gz_bridge` 설정. bridge 로그로 확인했고, `Twist`로 보내면 움직이지 않는다 |
| 통합에서 가장 어려웠던 점 | 리베이스 후 충돌 마커가 남은 채 push된 일. `colcon build`는 Python 문법 오류를 못 잡아 실행 확인과 `grep`을 절차에 넣었다 |
| 재현성은 어떻게 확인했나 | `run_restart_test.sh`로 실행·종료·재실행을 반복하고 남은 프로세스를 확인한다. 실험은 `SEED`로 순서를 재현한다 |

### B — 센서 처리·감지

| 질문 | 답변 요점 |
|---|---|
| 전방을 어떻게 판단했나 | 0번 샘플이 정면. 앞뒤 인덱스를 합친 ±15도 구간의 최소 유효 거리 |
| NaN, ±inf는 어떻게 처리했나 | REP 117 기준. +inf와 NaN은 제외, -inf는 너무 가까운 물체로 처리 |
| 센서 미수신은 어떻게 처리했나 | 전방 전체 NaN이면 발행하지 않고, avoider가 0.5초 뒤 안전 정지 |
| 왜 독립 계산으로 검증했나 | 같은 함수로 비교하면 구간 정의 오류를 찾을 수 없음 |
| 알려진 한계는 | 전방 구간 밖 장애물은 감지하지 못함. 오른쪽 경계가 -14.21도로 왼쪽보다 0.8도 좁다(샘플 한 칸 미만) |

### C — 회피·제어

| 질문 | 답변 요점 |
|---|---|
| 왜 상태 머신인가 | 감속·정지·회전·재주행이 순서가 있는 동작이라 상태로 나누면 전환 조건을 하나씩 시험할 수 있다 (TC-A1~A11) |
| 히스테리시스는 왜 넣었나 | 정지 0.5 m, 복귀 1.5 m. 같은 기준이면 경계에서 정지·전진이 반복된다 |
| 센서 사각지대는 어떻게 대응했나 | `/odom` 이동량으로 stuck을 감지해 후진·회전. 180초 안에 3회면 `GAVE_UP` 정지 |
| 성공률 9/10이면 충분한가 | 95% CI가 56~100%라 80% 이상이라고 단정할 수 없다. 그래서 30회로 늘렸고 29/30 이상이면 CI 하한이 목표를 넘는다 |
| 접촉 의심 1회의 원인은 | 시점별 기록(`avoid_trace`)으로 최소 거리가 나온 방향과 그때의 명령을 본다. 결과는 11일차 측정 후 답한다 |

### 공동 — QoS 실험

| 질문 | 답변 요점 |
|---|---|
| RELIABLE과 BEST_EFFORT 차이는 | RELIABLE은 재전송으로 손실을 막고 BEST_EFFORT는 재전송이 없다. BEST_EFFORT pub과 RELIABLE sub은 연결되지 않는다 |
| 3회 반복으로 결론을 낼 수 있나 | 없다. 대응 검정 최소 p가 0.25라 원리상 유의할 수 없어 10회로 늘렸다 |
| 메시지 수천 개인데 왜 표본이 10개인가 | 한 실행 안의 메시지는 서로 독립이 아니다. 메시지 단위로 검정하면 p값이 과도하게 작아진다(유사반복) |
| 실행 순서를 왜 섞었나 | 고정 순서면 시간에 따른 변화가 특정 조건에 몰려 QoS 효과처럼 보인다 |
| 손실이 0%면 실패한 실험인가 | 아니다. 로컬 환경의 사실을 그대로 기록했다. 손실을 임의로 만들지 않는다는 원칙을 계획서에 정해 두었다 |
