# 브랜치 전략 (Branching Strategy)

> 1일차 — A: 저장소 구조와 브랜치 규칙 정리

## 기본 원칙

- `main`: 항상 실행 가능한 안정 버전만 유지한다. 직접 커밋하지 않고 PR을 통해서만 병합한다.
- 작업 브랜치: GitHub 이슈를 먼저 만들고, 이슈 번호를 앞에 붙인 `{이슈번호}-{닉네임}` 형식으로 생성한다.
- `integration`: 팀원들의 작업 브랜치를 모아 통합 테스트하는 브랜치. **현재는 사용하지 않는다.** (아래 "PR 및 통합 절차" 참고)

## 브랜치 네이밍 규칙

형식: `{이슈번호}-{닉네임}`

| 이슈 | 닉네임 | 브랜치명 |
|---|---|---|
| #1 | ryubengock | `1-ryubengock` |
| #12 | ryubengock | `12-ryubengock` |

- 작업 종류(기능, 버그 수정, 문서, 실험)는 브랜치명이 아니라 **이슈 제목과 내용**으로 구분한다.
- 같은 이슈를 여러 명이 나눠 작업하면 같은 이슈 번호에 각자의 닉네임을 붙인다.

## 커밋 메시지 규칙

`[담당자] 유형: 설명` 형식을 사용한다.

- 유형: `feat`, `fix`, `docs`, `test`, `refactor`, `chore`
- 예: `[B] feat: /scan 구독 노드 기본 구현`

## PR 및 통합 절차

> 현재는 `integration` 브랜치를 건너뛰고 작업 브랜치에서 **`main`으로 바로 PR**을 생성한다. 팀 규모와 작업량이 늘어 통합 테스트가 필요해지면 `integration` 브랜치를 만들고 아래 원래 절차로 전환한다.

**현재 절차**

1. 작업 브랜치(`{이슈번호}-{닉네임}`)에서 작업 후 `main`으로 PR을 생성한다. PR 설명에 `Closes #{이슈번호}`를 적는다.
2. A가 인터페이스 호환성과 실행 여부를 확인한 뒤 머지한다.
3. 매일 통합 실행을 확인한다 (`plans.md` 6장 일일 체크리스트 참고).

**`integration` 사용 시 절차 (보류)**

1. 작업 브랜치에서 작업 후 `integration` 브랜치로 PR을 생성한다.
2. A가 인터페이스 호환성과 통합 실행 여부를 확인한 뒤 머지한다.
3. `integration`이 안정화되면 주요 마일스톤(중간 시연, 최종 발표 전)에 `main`으로 병합한다.

## 리뷰 기준

- 인터페이스 변경(토픽명, 메시지 타입, QoS 등) 시 머지 전에 팀에 공유한다.
- 머지 전 해당 기능이 로컬 환경에서 정상 실행되는지 직접 확인한다.
